# 스터디 대시보드 사이트 — 설계 문서

- **작성일**: 2026-08-27
- **대상 저장소**: `slipp-study`
- **상태**: 승인됨 (구현 계획 수립 대기)

---

## 1. 목적

"AI 기획자가 되어보자" 8회차 스터디의 문서를 **Next.js 기반 문서 대시보드**로 만들어 Vercel에 배포한다. 목표는 세 가지다.

1. 스터디 자료(설명·진행 방식·회차별 대본·양식)를 읽기 좋은 대시보드로 제공한다.
2. 진행자의 **기획 의도와 방향성 로드맵을 시각화 자료로 공유**한다.
3. 팀원이 만든 **산출물을 한곳에 수집·축적**하고, 파일 추가만으로 목록이 자동 갱신되게 한다.

백엔드는 두지 않는다. 팀원에게 저장소 접근을 열어주고, 수정 → PR → 머지 시 Vercel이 자동 배포하는 흐름으로 운영한다.

## 3. 아키텍처

### 3.1 스택

- **Next.js 15 App Router** — 전 페이지 정적 생성(SSG)
- **Fumadocs** (`fumadocs-ui`, `fumadocs-core`, `fumadocs-mdx`) — 사이드바 · 우측 TOC · 검색 · 다크모드
- **Tailwind CSS** — Fumadocs 테마 위에 토스 디자인 시스템을 얹는다 (§6)
- **Pretendard Variable** — 한글 서브셋으로 self-host (§6.3)
- **TypeScript**

Fumadocs는 **레이아웃 골격과 문서 인프라(사이드바 트리, TOC 추적, 검색 인덱스, MDX 파이프라인)만** 가져다 쓰고, 시각 표현은 전부 토스 기준으로 덮어쓴다. Fumadocs 기본 테마의 색·타이포·테두리·간격을 그대로 두지 않는다.

런타임 서버, 데이터베이스, API 라우트를 두지 않는다. 모든 페이지는 빌드 시점에 정적 파일로 생성된다. Vercel 무료 티어(Hobby)로 운영 가능하다.

### 3.2 배포 흐름

```
로컬 편집 ─┐
           ├─→ GitHub 저장소 ─→ Vercel Git 연동
팀원 PR ───┘                     ├─ main push  → 프로덕션 자동 배포
                                 └─ PR 생성    → Preview URL 자동 생성
```

**PR Preview URL이 이 설계의 중요한 부분이다.** 팀원이 산출물 PR을 올리면 머지 전에 "내 글이 사이트에서 어떻게 보이는지" 링크로 확인할 수 있다. 기여 진입장벽을 낮추는 핵심 장치이므로, PR 템플릿에 이 사용법을 명시한다.

### 3.3 저장소 초기화

현재 이 디렉터리는 git 저장소가 아니다. 구현 첫 단계에 다음이 포함된다.

1. `git init`, 기본 브랜치 `main`
2. `.gitignore` — `node_modules/`, `.next/`, `.superpowers/`, `.omc/`, `.vercel/`, `.env*`
3. GitHub 저장소 생성 및 push
4. Vercel 프로젝트 연결 (프레임워크 프리셋: Next.js)

### 4.2 중복 원본 정리

현재 `weeks/`와 `notion/01~08`은 상대경로 링크 유무만 다른 **거의 동일한 내용 2벌**이다. 여기에 `content/docs/`가 생기면 3벌이 되어 관리가 무너진다.

**결정: `content/docs/`를 유일한 원본으로 삼는다.**

- `weeks/*.md` — `content/docs/weeks/*.mdx`로 이관 후 삭제
- `notion/01~08.md` — 삭제. Notion 붙여넣기가 다시 필요하면 `scripts/export-notion.ts`로 `content/docs/`에서 생성한다 (상대경로 링크 제거 + frontmatter 제거)
- `notion/00-proposal.md` — 유지
- `notion/09-ai-playbook.md` — `content/docs/how/ai-playbook.mdx`로 이관 후 삭제
- `README.md` — 사이트 배포 후 **저장소 안내문으로 축소**한다. 스터디 내용은 사이트 링크로 넘기고, README에는 "이 저장소는 무엇인가 / 로컬 실행법 / 산출물 올리는 법"만 남긴다

`scripts/export-notion.ts`는 실제로 Notion 붙여넣기가 필요해질 때 만든다. 지금은 만들지 않는다.

## 5. 커리큘럼 데이터 단일 원천

`content/data/curriculum.ts`에 8회차 정보를 배열 하나로 정의한다.

```ts
export type Stage = 'eye' | 'hand' | 'head'

export interface Week {
  no: number              // 1~8
  stage: Stage            // 눈 / 손 / 머리
  slug: string            // '01-kickoff'
  title: string           // '킥오프'
  headline: string        // 이번 시간에 하는 것
  deliverable: string     // 다음 시간까지 만들어 올 것
  preread?: string[]      // 미리 볼 것
}

/** 지금 진행 중인 회차. 스터디가 아직 시작 전이면 null. */
export const currentWeek: number | null = null
```

`currentWeek`는 진행자가 매주 손으로 고치는 값이다. 자동 추적(날짜 계산 등)을 두지 않는다 — 일정이 밀리는 게 정상이고, 자동화하면 틀린 값이 표시되기 때문이다. 이 값 하나가 **홈 상단 배너와 여정 맵의 현재 위치 마커**를 만든다.

이 배열 하나가 다음을 모두 생성한다.

- 홈(`index.mdx`)의 8회차 표
- `<JourneyMap />` 여정 맵
- 각 회차 페이지 상단의 회차·단계 배지
- 회차 간 이전/다음 이동
- `<ArchiveBoard />`의 회차 라벨과 정렬 순서

**해결하는 문제:** 현재 같은 8회차 표가 `README.md`에 두 번(한눈에 보기 / 상세 계획), 각 `weeks/*.md` 상단에 또 흩어져 있다. 커리큘럼이 한 번 바뀌면 손댈 곳이 5군데다. 이 배열이 유일한 수정 지점이 된다.

회차 문서 본문(타임테이블, 반박 질문, 숙제 완료 기준)은 MDX 파일에 그대로 두고, 위 메타데이터만 `curriculum.ts`에서 가져온다.

## 6. 디자인 시스템 — 토스 레퍼런스

Fumadocs 기본 테마를 쓰지 않는다. 토스(Toss)의 시각 언어를 기준으로 재정의한다.

### 6.1 원칙 4개

1. **테두리 대신 배경으로 나눈다.** `border`와 `box-shadow`를 기본적으로 쓰지 않는다. 영역 구분은 `--g50` / `--g100` 배경 블록으로 한다. 예외는 구분선이 꼭 필요한 곳(TOC 왼쪽 레일, 카드 내부 구분선) 뿐이고, 이때도 `--g200` 1px만 쓴다.
2. **색을 아낀다.** 파랑은 "지금 여기"에만 쓴다. 현재 회차, 현재 TOC 항목, 링크, 숙제 카드. 그 외 강조는 **굵기와 크기**로 만든다.
3. **여백이 위계를 만든다.** 요소 간 간격을 넉넉히 준다. 정보를 빽빽하게 채우지 않는다.
4. **한 화면에 한 가지 핵심.** 회차 문서에서 가장 중요한 것은 "다음 주까지 뭘 해야 하나"다. 이것이 본문에 묻히지 않고 독립된 카드로 서 있어야 한다.

### 6.2 색

Tailwind 테마에 CSS 변수로 정의한다.

**그레이스케일 (위계의 주력)**

| 토큰 | 값 | 용도 |
|---|---|---|
| `--g50` | `#F9FAFB` | 가장 옅은 블록 배경 |
| `--g100` | `#F2F4F6` | 블록 배경, 배지 배경 |
| `--g200` | `#E5E8EB` | 구분선, 비활성 바 |
| `--g300` | `#D1D6DB` | 비활성 바 (진한 쪽) |
| `--g500` | `#8B95A1` | **본문에 쓰지 않는다** — 아이콘, 플레이스홀더 전용 (§6.7) |
| `--g600` | `#6B7684` | 보조 텍스트의 하한선 |
| `--g700` | `#4E5968` | 본문 텍스트 |
| `--g800` | `#333D4B` | 강조 텍스트 |
| `--g900` | `#191F28` | 제목 |

**액센트**

| 토큰 | 값 | 용도 |
|---|---|---|
| `--blue` | `#3182F6` | 현재 위치, 링크, 숙제 카드 강조 |
| `--blue-bg` | `#E8F3FF` | 현재 항목 배경, 숙제 카드 배경 |
| `--red` | `#F04452` | 경고 (개인정보 배너 등) |
| `--green` | `#15C26B` | 완료 표시 |

**단계 틴트 — 사용처를 제한한다**

| 단계 | 바 색 | 칩 배경 / 칩 글자 |
|---|---|---|
| 👀 눈 (1~3회) | `#C6D8F5` | `#E8F1FC` / `#2C5FA8` |
| ✋ 손 (4~6회) | `#C2E6D2` | `#E3F5EA` / `#1E7A4C` |
| 🧠 머리 (7~8회) | `#F5D9C2` | `#FCEDE0` / `#9C5A26` |

**규칙: 단계 틴트는 `<JourneyMap />`의 바와 단계 칩에서만 쓴다.** 사이드바, 본문, 아카이브 필터, 버튼에는 쓰지 않는다. 이 제한이 없으면 색이 4개로 늘어난 만큼 절제가 무너진다. 현재 회차는 단계 틴트를 덮고 `--blue`로 칠한다.

**다크 모드**는 라이트를 기본값으로 두고 토글로 제공한다. 그레이스케일을 반전하되 순검정(`#000`)은 쓰지 않고 `#17171C` 계열을 배경으로 쓴다. 단계 틴트는 다크에서 채도를 더 낮춘 별도 값을 갖는다.

### 6.3 타이포그래피

토스체(Toss Product Sans)는 비공개 폰트라 사용할 수 없다. **Pretendard Variable**을 쓴다. CDN이 아니라 한글 서브셋을 `public/fonts/`에 두고 self-host 하며, `next/font/local`로 로드해 레이아웃 시프트를 막는다.

전 텍스트에 `letter-spacing: -0.02em`(제목은 `-0.03em`)을 적용한다. 한글에서 이 자간이 토스 특유의 밀도를 만든다.

| 역할 | 크기 / 굵기 | 색 |
|---|---|---|
| 문서 제목 | 30px / 800 | `--g900` |
| 리드 문장 | 15px / 400 | `--g600` |
| 섹션 제목 | 19px / 800 | `--g900` |
| 본문 | 15px / 400, 행간 1.75 | `--g700` |
| 보조 · 캡션 | 12.5px / 400 | `--g600` |
| 사이드바 항목 | 13.5px / 400 | `--g600` |

숫자는 `font-variant-numeric: tabular-nums`를 적용한다 (회차 번호, 시간, 날짜 정렬).

### 6.4 표면과 간격

- 모서리: 카드 `16px`, 배지·칩 `999px`(pill), 사이드바 항목 `8px`, 작은 블록 `10px`
- 카드 내부 여백: `17~19px`
- 본문 최대 폭: `640px`. Fumadocs 기본값보다 좁게 잡아 읽기 리듬을 유지한다
- 섹션 제목 위 여백 `34px`, 아래 `12px`

### 6.5 반응형 — 모바일 우선

온라인 스터디라 폰으로 보는 비중이 높다. 다음을 명시적으로 설계한다.

| 화면 | 레이아웃 |
|---|---|
| `≥1280px` | 사이드바 · 본문 · TOC 3열 |
| `1024~1279px` | 사이드바 · 본문 2열 (TOC 숨김) |
| `<1024px` | 본문 1열. 사이드바는 햄버거 드로어, TOC는 제목 아래 접이식 |

**가로로 그린 것은 모바일에서 전부 다시 배치한다.**

- `<TwoHourBlock />` — 데스크톱에서도 **세로 스택**으로 그린다. 가로 120분 바는 모바일에서 텍스트가 안 들어간다. 세로가 "어디에 시간을 쓰는가"를 더 잘 보여주기도 한다
- `<JourneyMap />` — 데스크톱 8칸 가로. 모바일에서는 **가로 스크롤 + 스냅**, 현재 회차로 자동 스크롤
- `<ThreeStages />` — 3칸 가로 → 세로 스택
- `<Roadmap />` — 수평 타임라인 → 세로 타임라인

**기존 문서의 표를 처리한다.** README와 `weeks/`는 표가 지배적인데(8회차 표, 용어 사전 20행, 회차별 계획 3개 표), 모바일에서 가로 스크롤이 된다.

- **8회차 표** → `<JourneyMap />`과 회차 카드 리스트로 대체. 표를 남기지 않는다
- **용어 사전** → `<Glossary />` 검색 가능 아코디언으로 대체 (§7.2)
- **회차별 상세 계획 표 3개** → `how/three-stages.mdx`에서 단계별 카드 리스트로 변환
- **그 외 표** — 표로 두되, `<1024px`에서 가로 스크롤 컨테이너에 넣는다. 페이지 전체가 가로로 밀리지 않게 한다

### 6.6 카피 톤

토스 카피는 `~해요` 체다. 다만 기존 문서 3,700줄은 `~합니다` 체이고, "반박", "전원 공격" 같은 강한 어휘가 이 스터디의 정체성이다. 전면 전환은 문서 재작성이므로 하지 않는다.

**규칙: UI 요소는 `~해요`, 문서 본문은 원문 유지.**

- `~해요`를 쓰는 곳: 섹션 제목, 빈 상태 문구, 안내·도움말, 버튼, 검색 플레이스홀더, 배지 라벨
  - 예: "2시간을 이렇게 써요", "무엇이 궁금하세요?", "아직 제출물이 없어요"
- 원문 유지: 회차 문서 본문, 양식, AI 플레이북, 용어 정의

### 6.7 접근성

토스 감성을 따라가다 회색을 연하게 쓰면 대비가 무너진다. 다음을 강제한다.

- **본문·보조 텍스트에 `--g500`(`#8B95A1`)을 쓰지 않는다.** 흰 배경 대비 약 3.5:1로 WCAG AA(4.5:1) 미달이다. 보조 텍스트의 하한은 `--g600`(`#6B7684`)이다
- `--g500`은 아이콘, 비활성 플레이스홀더 등 **텍스트가 아닌 요소**에만 허용한다
- 단계 칩은 배경과 글자 조합(예: `#E8F1FC` / `#2C5FA8`)으로 AA를 만족시킨다. 틴트 배경 위에 연회색 글자를 올리지 않는다
- 단계 구분을 **색에만 의존하지 않는다.** 이모지(👀 ✋ 🧠)와 텍스트 라벨을 항상 함께 둔다 — 색각 이상 사용자와 흑백 인쇄 모두를 위해서다
- 포커스 링을 지우지 않는다. `--blue` 2px 아웃라인으로 표시한다

### 7.3 아직 내용이 없는 자료 (④⑤)

④는 진행자가 의도를 제공해 **내용까지 채운다.** ⑤는 아직 내용이 없어 **구조만 만들고 데이터는 플레이스홀더로 둔다.**

- `content/data/why.ts` — **세 칸 모두 채운다.** 진행자가 의도를 제공했다: 1인 사업에 필요한 능력이 기획·개발·마케팅으로 갈리는데 개발자는 개발만 갖고 있고, 만들 줄 아는 것이 오히려 함정이 된다는 진단. 설계 결정 칸은 시장 분석 → 프로덕트·서비스 기획 집중, 반박 40분, 마지막 2주 실검증

플레이스홀더 상태에서도 페이지는 정상 렌더링되어야 하며, 화면상 "작성 예정"임이 드러나야 한다. 빈 문자열로 레이아웃이 깨지지 않게 한다. 반대로 **플레이스홀더가 0개인 상태**(현재 `why.ts`)에서도 테스트와 렌더링이 깨지지 않아야 한다.
## 8. 아카이브

### 8.1 파일 규약

`content/docs/archive/` 아래에 `.mdx` 파일을 추가한다. 파일명 규약: `w{회차 2자리}-{영문 이름}-{종류}.mdx` (예: `w05-hong-interview.mdx`).

frontmatter 5개 필드가 필수다.

```yaml
---
title: 당근마켓 역기획
week: 2                # 1~8
author: 홍길동
type: 역기획            # 역기획 | PRD | 인터뷰 | 지표트리 | 원페이저 | 검증결과
date: 2026-09-15
---
```

### 8.2 자동 집계

`<ArchiveBoard />`가 빌드 시점에 `archive/` 콜렉션 전체를 읽어 목록을 생성한다. **수동 관리하는 목록 파일을 두지 않는다.** 파일 하나를 추가하면 목록에 자동으로 나타난다.

제공하는 뷰:

- **회차별** — 1~8회차 섹션, 각 회차 아래 제출물. 미제출 회차는 빈 상태로 표시
- **작성자별** — 이름별 그룹
- **종류별 필터** — 6종 타입 칩

`archive/meta.json`은 `index.mdx`만 사이드바에 노출하고 개별 제출물은 사이드바에서 숨긴다(`pages: ["index"]`). 제출물이 20~40개로 늘어나도 사이드바가 무너지지 않는다. 개별 문서는 `<ArchiveBoard />`를 통해서만 진입한다.

### 8.3 개인정보 보호

5주차 산출물은 실제 인터뷰 기록이고 사이트는 전체 공개다. 정책을 문서에 쓰는 것만으로는 지켜지지 않으므로 두 개의 장치를 둔다.

1. **`templates/interview.mdx` 최상단 고정 배너** — 가명 처리 규칙을 양식 자체에 못 박는다. 인터뷰이는 `A씨(30대 직장인)` 형태로만 기록하고, 실명·회사명·연락처·녹취 원문·스크린샷은 올리지 않는다
2. **`.github/PULL_REQUEST_TEMPLATE.md` 체크박스** — "실명·회사명·연락처를 제거했습니다" 항목을 체크해야 PR을 올릴 수 있게 안내

### 8.4 팀원 기여 흐름

```
저장소 접근 권한 부여
  → 브랜치 생성
  → content/docs/archive/wNN-name-type.mdx 추가
  → PR 생성
  → Vercel Preview URL로 렌더링 확인
  → 머지 → 프로덕션 자동 배포
```

이 절차를 `templates/` 그룹 안이 아니라 **저장소 `README.md`와 PR 템플릿 양쪽에** 적는다. 사이트를 안 거치고 GitHub만 보는 사람도 있기 때문이다.

## 9. 오류 처리와 검증

정적 사이트이므로 런타임 오류 처리보다 **빌드 타임 검증**이 방어선이다.

| 검증 대상 | 방법 | 실패 시 |
|---|---|---|
| frontmatter 필드 | `fumadocs-mdx` 콜렉션의 zod 스키마 (`archive`는 `week`/`author`/`type`/`date` 필수, `type`은 enum) | 빌드 실패 |
| `week` 범위 | zod `.min(1).max(8)` | 빌드 실패 |
| 문서 간 링크 | 빌드 후 내부 링크 검사 스크립트 | 빌드 실패 |
| `curriculum.ts` ↔ `weeks/` 파일 | 8개 slug가 실제 MDX 파일과 1:1 대응하는지 검사 | 빌드 실패 |
| `<Term />` 용어 | 본문에서 참조한 용어가 `glossary.ts`에 있는지 검사 | 빌드 실패 |
| 타입 | `tsc --noEmit` | 빌드 실패 |

`pnpm build`가 이 검증을 모두 통과해야 한다. Vercel이 PR마다 빌드하므로, 잘못된 frontmatter를 가진 PR은 머지 전에 실패로 드러난다. **별도 CI 설정 없이 Vercel 빌드 자체가 게이트가 된다.**

**빈 상태를 설계한다.** 다음은 모두 정상 화면이어야 하며, 깨진 레이아웃이나 빈 공백으로 보이면 안 된다.

- `<ArchiveBoard />` 제출물 0개 — 스터디 시작 전에는 이게 기본 상태다. "아직 제출물이 없어요" + 올리는 법 링크
- `currentWeek`가 `null` — 홈 배너가 사라지고, 여정 맵에 현재 위치 마커가 없다
- `why.ts` / `roadmap.ts` 플레이스홀더 — "작성 예정"임이 화면에 드러난다

**수동 검증 항목** (빌드로 못 잡는 것)

- 360px 폭에서 모든 페이지가 가로 스크롤 없이 읽힌다. 표는 자기 컨테이너 안에서만 스크롤된다
- 라이트·다크 양쪽에서 §6.7의 대비 기준을 만족한다
- 키보드만으로 사이드바 → 본문 → TOC 이동이 되고 포커스 링이 보인다

## 10. 알려진 리스크

**Fumadocs 내장 검색(Orama 정적 검색)의 한국어 처리.** 한국어는 형태소 분리가 필요한데 기본 토크나이저가 공백 기준이라, "기획"으로 검색했을 때 "역기획" 문서가 안 잡힐 수 있다. 구현 단계에서 실제 문서로 검증하고, 결과가 나쁘면 대안(Pagefind 등)으로 교체한다. **스택 선택을 되돌릴 만한 리스크는 아니다** — 검색은 교체 가능한 부품이고 나머지 기능은 영향받지 않는다.
