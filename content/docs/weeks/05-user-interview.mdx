> **이번 회차 한 줄 목표**
> 기업의 실제 반응을 바탕으로 제안의 강점과 부족한 점을 찾고, **개선으로 이어질 다음 행동**을 정한다.

| 구분 | 내용 |
|---|---|
| 단계 | ✋ 2단 — 손 (기법) |
| 미리 해올 것 | 전달한 제안서·발송 기록·기업 답변 또는 미응답 기록 |
| 이번 회차 산출물 | 피드백 정리 + 제안 보완본 + 다음 행동과 선택 이유 |
| 다음 회차 연결 | 개선안의 성공 기준과 우선순위 정리 |

4회차에서 동료를 설득하며 다듬은 제안을 실제 기업에 전달했다. 이번에는 “어떤 반응을 얻었나”를 공유하고, 사용자 입장의 불편을 기업이 실행할 수 있는 제안으로 바꾸려면 무엇이 더 필요한지 논의한다.

**기업의 답변이나 실제 반영은 우리가 통제할 수 없다.** 이번 회차의 완료 기준은 답변 수가 아니라, 전달 과정과 반응을 정확히 기록하고 그 결과로 제안을 개선하는 것이다.

## 준비할 기록

| 항목 | 설명 |
|---|---|
| 원래 제안 | 서비스·불편·핵심 개선안·기업에 요청한 내용 |
| 전달 과정 | 언제, 어떤 공식 채널로, 어떤 문서와 메시지를 보냈나 |
| 실제 반응 | 답변 원문과 날짜, 자동 접수 여부, 또는 기준일 현재 미응답 |
| 내 해석 | 상대가 이해한 점, 우려한 점, 설명이 부족했던 점 |
| 보완안 | 무엇을 바꾸고 무엇을 유지할 것인가 |
| 토론 질문 | 실제 개선으로 연결하려면 어떤 선택이 필요한가 |

스터디에서 공유할 때는 담당자의 이름·연락처 등 개인정보를 가린다. 답변을 인용한 부분과 내 해석은 구분한다.

## 답변 상태를 어떻게 읽을까?

| 상태 | 의미 | 토론할 지점 |
|---|---|---|
| 미응답 | 기록 기준일까지 답변을 받지 못함 | 전달 채널과 요청이 적절했나? 기다리거나 접근 방식을 바꿀 이유가 있나? |
| 자동 접수 안내 | 시스템이 문의를 접수했다는 안내 | 제안 내용에 대한 검토 결과로 해석하지 않기 |
| 정책·사용법 안내 | 현재 방식과 사용 방법을 설명받음 | 안내 부족이 문제였나, 사용법으로도 해결되지 않는 불편인가? |
| 보류·거절 | 답변에 보류나 반영 불가 이유가 명시됨 | 비용·정책·대상 범위 등의 이유를 반영해 대안을 줄일 수 있나? |
| 검토 의사 | 검토하겠다는 답변을 받음 | 추가 설명 요청이 있나? 반영 확정으로 해석하지 않기 |
| 실제 반영 확인 | 변경된 동작이나 공개 안내를 확인함 | 제안한 불편이 실제로 줄었나? 내 제안 때문에 바뀌었다는 인과는 확인 가능한가? |

개선으로 이어진 사례가 없어도 회차를 진행한다. 상대의 답변이 없거나 제안이 받아들여지지 않은 이유를 살펴보는 것도 학습 자료다.

### 발표 순서

1. 어떤 불편과 개선안을 보냈나?
2. 어디에 어떤 요청으로 전달했나?
3. 실제로 받은 답변은 무엇인가? 미응답이면 언제까지 확인했나?
4. 답변을 보고 내 생각이 어떻게 달라졌나?
5. 무엇을 보완하고, 다음에는 어떤 행동을 하려 하나?

발표의 중심은 답변을 받았다는 사실보다 **그 반응으로 무엇을 배웠는지**다. 다른 팀원은 기업 입장과 사용자 입장을 번갈아 검토한다.

## 토론: 어떻게 실제 개선으로 이어지게 할까?

### 1. 문제 전달이 충분했나?

- 담당자가 같은 불편을 재현할 수 있게 상황과 순서를 설명했나?
- 개인 취향과 작업을 막는 불편을 구분했나?
- 상대가 답해야 할 요청이 너무 많거나 모호하지 않았나?

### 2. 기업이 검토할 이유가 있었나?

- 사용자에게 생긴 영향이 구체적인가?
- 반복 문의·실수·이용 포기 등에 대한 근거가 있는가, 추측인가?
- 기업의 정책과 운영 제약을 답변에서 새로 알게 됐나?

### 3. 더 작은 대안이 있나?

- 큰 기능 개발 대신 안내 문구·정보 위치·상태 표시로 해결할 수 있나?
- 전체 사용자 대상보다 특정 상황에만 적용할 수 있나?
- 원래 제안과 작은 대안 중 어떤 쪽을 먼저 제시할까?

### 4. 어떤 다음 행동이 적절한가?

- 답변에 맞춰 설명과 문서를 보완한다.
- 추가 질문이 있으면 필요한 근거만 정리한다.
- 제안 접수 채널이 따로 있다면 해당 절차를 확인한다.
- 미응답이면 확인 시점과 기다릴 이유를 정한다.
- 기업이 명확히 반영 불가라고 설명했다면 그 이유를 기록하고 다른 대안을 평가한다.

정해진 답은 없다. **각자 선택한 행동과 그 이유**를 남긴다. 반복 발송 횟수나 답변을 받아내는 것을 성과로 삼지 않는다.

## 회차에서 완성할 문서

```text
[서비스 개선 제안 결과]

1. 원래 문제와 개선안
2. 발송 기록: 날짜 / 채널 / 문서 / 요청 내용
3. 실제 답변 또는 기준일 현재 미응답
4. 답변 원문과 내 해석
5. 동료 토론에서 나온 의견
6. 보완할 점과 유지할 점
7. 다음 행동: 무엇을 / 언제 / 왜
8. 실제 개선 여부를 확인할 방법
```

마지막 항목은 예를 들어 “취소 상태를 주문 화면에서 바로 확인할 수 있는가”처럼 **사용자 행동이나 서비스 동작**으로 적는다. 검토하겠다는 답변만으로 개선 완료라고 적지 않는다.

### 완료 기준

- [ ] 발송한 문서와 전달 경로를 공유했다.
- [ ] 답변·자동 안내·미응답 상태를 구분했다.
- [ ] 기업 답변의 사실과 내 해석을 나눠 적었다.
- [ ] 토론 후 제안을 보완하거나 유지한 이유를 기록했다.
- [ ] 다음 행동과 개선 여부를 확인할 기준을 정했다.
